# Compliance roadmap

Prioritised backlog from [`GAP-ANALYSIS.md`](GAP-ANALYSIS.md). Effort: S (under a day), M (1-3 days), L (a week or more).
Frameworks: S = SOC 2, I = ISO 27001:2022, P = PIPEDA. Completing items makes Toolkit better
placed for an audit; it does not by itself make it certified or compliant.

## Technical (code)

Ordered by value. Each item's acceptance criteria are meant to be handed to an engineer as-is, and
each should land with a test in `test/`.

| ID | Title | Serves | Effort | Acceptance criteria |
|---|---|---|---|---|
| T-01 | **Done 2026-11-22.** TOTP multi-factor authentication | S CC6.1; I 5.17, 8.5; P 4.7 | L | (1) Account page can enrol an authenticator app (RFC 6238, 30 s step, SHA-1, 6 digits, +/-1 step window) with QR and manual key, shown once. (2) Secret stored encrypted at rest, never logged or exported. (3) 10 single-use recovery codes, stored hashed, regenerable. (4) Password login and Google-only accounts both require the second factor when enabled; failed codes limited like `loginLimiter` and audited (`mfa.fail`, `mfa.enable`, `mfa.disable`). (5) Disabling or changing requires re-authentication. (6) Codes cannot be replayed within their window. (7) Operator setting `TOOLKIT_REQUIRE_MFA` forces enrolment at next sign-in. (8) Tests cover enrol, login, replay, lockout, recovery, desktop flow. |
| T-02 | **Done 2026-11-22.** Remove `style-src 'unsafe-inline'` | S CC6.8; I 8.26, 8.28 | L | (1) `server/index.js` CSP has no `'unsafe-inline'` in `style-src` and none in `script-src`. (2) All inline `style=` attributes and `style.cssText` in Sigma, Pigment, ImageVendor, Placeholder and shell pages replaced by classes or CSSOM property sets (`el.style.prop = ...` is allowed). (3) security.test asserts the header value. (4) `test/browser-smoke.cjs` passes with zero CSP violation console messages in all four apps. (5) SVG dynamic styling verified visually. |
| T-03 | CI pipeline with tests, dependency audit and secret scanning | S CC7.1, CC8.1; I 5.7, 8.8, 8.25, 8.28, 8.32 | M | **Prepared 2026-11-22; activates on first push (owner applies GITHUB-SETTINGS.md).** (1) `.github/workflows/ci.yml` runs on every push and pull request: `npm ci`, `npm test`, `npm audit --omit=dev --audit-level=high` (fail the build), and a verification of installed versions (see SECURITY-ASSESSMENT F-05 note). (2) Secret scan (gitleaks or GitHub secret scanning + push protection) enabled and failing on findings. (3) CodeQL or equivalent SAST for JavaScript, results visible. (4) Dependabot (or Renovate) for npm and GitHub Actions. (5) Actions pinned to commit SHAs; least-privilege `permissions:`. (6) A licence report artefact (lamejs LGPL noted). (7) Branch protection on `main` requires the checks (see O-08). |
| T-06 | Off-machine encrypted backups with restore test | S A1.2, CC7.5; I 8.13, 5.30; P 4.7 | M | (1) A script (`scripts/backup.cjs`) copies `db.json` and `audit/` to a configured destination (local path or S3-compatible bucket) using an encrypted, versioned format; the key for the backup is not stored with the backup. (2) Runs on a schedule (systemd timer example in `deploy/`; Windows Task Scheduler instructions for desktop). (3) Retention pruned to the policy value (default 30 days) and logged. (4) `scripts/restore-test.cjs` restores into a temp dir, opens the store, verifies the audit chain and prints counts; exit non-zero on failure. (5) Failure raises an alert (see T-04). (6) Tests cover backup, prune and restore. (7) Restore test result recorded in `policies/backup-and-continuity.md` evidence log. |
| T-04 | Log export and alerting | S CC7.2, CC7.3; I 8.15, 8.16, 5.28; P 4.7 | M | (1) Audit events can be streamed or shipped (append-only file shipper or syslog/HTTPS sink) to off-host storage via env configuration; the hash chain is preserved. (2) Alert rules, evaluated at least every 5 minutes: more than N `login.fail`/`login.locked` per window, `csrf.blocked` spike, `quota.exceeded`, `verify-audit` failure, backup failure, store write failure. (3) Alerts delivered by email (reusing `mailer.js`) or webhook to `TOOLKIT_ALERT_TARGET`; rate-limited so a storm yields one message. (4) `/healthz`-style endpoint (no data) for uptime monitoring. (5) Tests with fake sink. |
| T-05 | Signed Windows installer | S CC6.8; I 8.1, 8.7 | M | (1) `desktop/builder.cjs` signs the NSIS installer and app binary with a code-signing certificate (key held in an HSM/cloud signer or CI secret, never in the repo). (2) `Get-AuthenticodeSignature` shows Valid with timestamp. (3) SHA-256 of each release published next to the installer. (4) Build record (version, date, commit) kept per release (see memory rule: keep every installer, new version per change). (5) Update path documented (manual or signed auto-update with signature verification). |
| T-07 | Encryption at rest required by default when hosted | S C1.1; I 8.24; P 4.7 | S | (1) `server/hosted.cjs` refuses to start without `TOOLKIT_DATA_KEY` unless `TOOLKIT_ALLOW_PLAINTEXT=1` is set, which prints a warning. (2) Desktop mode generates a per-install key stored via Electron `safeStorage` (or documented decision not to). (3) Tests for refusal and override. |
| T-08 | Admin access review tooling | S CC6.2, CC6.3; I 5.18, 8.2, 8.18 | M | (1) `scripts/admin.cjs access-report` prints every account with created date, last sign-in, auth methods (password, Google), email-confirmed state, active session count, and flags dormant (over 180 days) and unconfirmed accounts. (2) Output is CSV/JSON with no hashes or tokens; the run itself is audited. (3) A review record format (date, reviewer, actions) is stored in `docs/compliance/evidence/` or the audit log (`admin.access_review`). (4) Optional `disable <email>` that blocks sign-in without deleting. (5) Tests. |
| T-09 | Breach notification support | P breach provisions; S P6; I 5.24-5.26 | M | (1) `scripts/admin.cjs notify --subject --body-file --filter ...` sends a plain-text notice through `mailer.js` to a selected set of confirmed addresses, dry-run by default, rate-limited, each send audited. (2) `scripts/admin.cjs breach-log add/list` keeps the PIPEDA breach record (fields from `policies/incident-response.md`) with 24-month minimum retention that is never auto-purged. (3) Tests. |
| T-11 | Self-service email change with code confirmation | P 4.6; S P7 | M | (1) Signed-in user, after re-authentication, requests a new address; a 6-digit code is sent to the new address; the address changes only after the code is entered. (2) Old address is notified. (3) Same provider and deliverability checks as sign-up. (4) Sessions other than the current one end. (5) Audited and tested. |
| T-12 | Policy re-consent and Terms acceptance record | P 4.3; S P2 | S | (1) When `PRIVACY_VERSION` (or a new `TERMS_VERSION`) changes, signed-in users must accept before continuing; version and time stored. (2) Sign-up records both versions. (3) Tests. Depends on the Terms and Privacy drafts being finalised. |
| T-13 | Optional hardening backlog | S CC6.1; I 8.5 | M | Passkeys (WebAuthn) as an alternative to TOTP; breached-password (k-anonymity) check; account-lockout notification email; session binding to coarse client signature. Each needs its own acceptance criteria before work starts. |

## Organisational (owner and policy)

| ID | Title | Serves | Effort | Acceptance criteria |

| O-01 | Approve the ISMS policy set | S CC1, CC5; I 4, 5, 5.1-5.4, 5.10 | M | Named owner for each file in `policies/`; DRAFT headers removed; approval date and approver recorded; ISMS scope, interested parties and objectives written; policies communicated to everyone with access; calendar review dates set |
